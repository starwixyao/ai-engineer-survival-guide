先立三块基石：Token / 上下文 / 参数——被误用最多的三个词

Token · 最小积木

模型读写的最小单位。英文 ≈0.7 词/token；中文 1 字 ≈1-2 token，取决于分词器。

"Harness 工程"
→ ["Har","ness"," 工","程"]

误解：1 个字 = 1 个 token。
计费、窗口长度、输出速度都按 token 算。

上下文 · 一次推理的视野

每次请求模型"一次能看见"的全部内容上限。不是记忆容量，是视野。

第1轮 [系统+用户1]
第2轮 [系统+用户1+助手1+用户2]
第N轮 [……全部历史……]

误解：它记得我们聊过的历史。
历史每轮重新发送：越长越贵、越易稀释。

参数 · 冻结的倾向

训练固化下来的上万亿个数字，决定"猜"的倾向。训练结束时冻结 ❄，与你对话时不变。

误解："它从我这儿学到了"。
"它学到了"只发生在你的上下文里——这是理解"记忆"的钥匙（P42）。

搞混这三个词，后面全乱：计费按 token，失忆按上下文，"学不会"按参数。

temperature 控制的是胆量，不是智商

档位行为场景
T→0几乎总选最高概率词（greedy），稳定可复现写代码、抽取类任务
T=1按原始分布抽签，自然、多样对话、写作

无状态推理：每轮都是"从零开始"

中间会"失焦"：Lost in the Middle

关键信息放长上下文中间位置时，利用率明显下降（Liu et al., 2023）。开头与结尾更"响"，中段最容易被忽略——而且它不会告诉你"我没读到"。

推论与 Harness 落点

  • 对话越长，最早的约束越容易被淹没（→ 顽疾④）
  • 换一个会话 = 换一个"新员工"（→ 记忆落盘 P40）
  • 关键约束放开头或结尾，别埋中间；结论类信息写进文件

比喻：一个每天上班失忆的同事

交接班必须靠交接文档，不能靠"他应该记得"。

它仍然用同样的自信回答你：给你 2024 年最流行的写法，一句提醒都没有。旧写法在语料里出现得更多 → 概率更高 → 它反而"更确信旧的"。

  • 工具：让它读 lock 文件、查文档、跑命令，先看再写
  • 知识注入：把"当前版本 + 关键变更"放进上下文（→ 顽疾②，P26）

两条时间线

可验证的推断：让它写"最新写法"，再问"这是哪一年的"——两个答案往往互相矛盾。

四个要素，各自的不可替代性

◆ 模型

= 决策。决定下一步；它仍然只会"猜"，只是猜完能动手了。

◇ 工具

○ 循环

= 耐心。一次不对就再来，ReAct 把"想"和"做"交替起来。

= 眼睛。stdout、退出码、测试结果。没有观察，纠正无源之水。

Harness：这个词不是比喻

工程定义

Harness = 包裹在模型之外的运行时：上下文装配、工具提供、权限控制、沙箱执行、记忆检索、验证与回放。不是某个具体产品，是一类系统的名字。

为什么"马具"这个词是准确的

  • 马有力气——模型会生成、会推理
  • 但牵不动车——它不会自己交付，也不负责后果
  • 套上马具才成为运输力——力气被导向你要的方向
鞍 = 工具
缰绳 = 权限
头套 = 上下文裁剪
鞍垫 = 记忆

马具不是"限制"：缰绳让马走你要的方向，轭把力气接到车上——每一件都在扩大"可用"的范围。同一匹马：不给权限会踩坏地板，给权限能拉货；装上眼罩不被路边分心（=上下文裁剪）。

一条乘法公式

Agent 能力 ≈ 模型 × Harness × 环境
任一项 ≈ 0，整体 ≈ 0
—— "模型很强但用起来很笨"的解释

三个词别混

Agent 是角色（谁干活）· Harness 是装备（怎么干）· 环境 是场地（在哪干：git/测试/CI）

2026 工程共识

当生成变便宜，"能不能做出来"不再稀缺。稀缺的是可靠、可信任地做完、做对、之后还能改。旧问题 Can it build it? → 新问题 Can I trust it?

马具放大了马的力气，也放大了马的毛病

第一幕结论

它只会猜：不查真值、像先于对、没见过就编、每次抽签

第二幕结论

合起来

猜错一次的代价，被乘以执行次数 × 文件数量 × 自动化程度

四条放大链

  • 干得越多 → 错的传播面越大：一次幻觉写进 20 个文件（不再是一段回答）

  • 干得越自动 → 越需要闸门：没人盯着时，权限是唯一护栏
  • 干得越快 → 越需要验证：人的验收速度成为新瓶颈

第2档 写入

STOP 1 先开分支/打快照出事能退，才敢让它跑长任务
STOP 2 先出 diff，不直接执行看清楚要改什么，再放行
STOP 3 高危命令人看清再放展示完整命令，不折叠
ALLOW read · grep · git log只读动作不打扰人

压缩怎么压：四种手段，四种代价

所有压缩都是有损的。工程上要做的不是"不丢"，而是先决定丢什么可以接受

手段做法保住了丢了适用
① 截断只保留最近 N 轮 / 截首尾，超出部分丢弃最近的对话与最新报错最早的约束与需求原文短任务、探索性会话
② 摘要用小模型把历史压成几段话（/compact）梗概、目标、阶段性结论精确标识符、行号、报错原文长任务中段、阶段切换
③ 分层保留规则/目标常驻，历史可压，工具输出先摘要再入规则与目标（最高价值）中间过程细节几乎所有长任务
④ 外部化+检索回填历史落盘成文件/记忆，需要时按关键词取回几乎全部（可重新取回）召回延迟；索引要维护跨会话、跨天任务

实践组合：③ 为默认骨架，② 为中段瘦身，④ 承接跨会话，① 只用于抛弃型会话。压缩前给显式保留清单（"务必保留：xx 约定 / yy 接口签名"）。

CH4 · 上下文工程 4/6

压缩之后丢掉了什么：摘要 ≠ 事实

压缩前 · 原始记录

约束  改用 v2 API，必须
      兼容旧参数 page=……
read retry.go:42  (报错原文)
决定  弃用方案B，因为
      ……不兼容锁文件
run test → 3 failed (日志4KB)
→

压缩后 · 摘要

"在做缓存优化，
  处理过一些测试问题，
  后续继续完善"

约束变陈述，行号没了，
"弃用方案B"的理由蒸发

三类系统性损失

  • 细节：精确行号、变量名、参数签名 → "记得改过，不知道在哪"
  • 约束弱化："必须兼容 v2"被压成"做了 v2"——命令变陈述，失去约束力
  • 隐性共识蒸发："为什么不用方案 B"没进摘要 → 它又把 B 提回来

更隐蔽的：摘要也会"编"

摘要由模型生成，同样有幻觉风险；写错一个词（"进行中" vs "已删除"）就污染后续所有轮次。压缩一次 = 引入一次失真机会。

事故复现：幽灵代码

step20 删除 legacyCache 模块
step40 自动压缩 → 摘要写：
       "缓存逻辑优化(进行中)"
step41 "继续完善缓存，我恢复了
       legacyCache 并扩展…"
已删除的代码回来了

止损规则

  • 压缩前给显式保留清单
  • 关键事实落盘（git/文件），不依赖窗口存活
  • 压缩后立刻跑测试验证现场一致
  • 小步多压 > 一次救火式大压

三层装配（每轮请求的组织方式）

常驻层

≤几十行：系统提示、项目规则、今天日期、关键禁区。每轮都在，缓存友好。规则越少越被遵守。

  • 引用思维：窗口里放路径+摘要，需要时再读全文

反模式为什么错替代做法
✗ 把整个仓库塞进上下文稀释 + 昂贵 + 中段遗忘检索优先精选进入；工具输出先摘要
✗ "通过测试 = 正确"测试本身也可能不全测试即规格 + 独立复核 + 人工清单
✗ 迷信单一模型/单点榜单任务差异 + 档位差异（P12）看区间、看成本、按任务选
✗ 不设权限追求"全自动"一次误删就是事故（P30）三档闸门 + 可回滚 + 高危转人工
✗ 没有验收标准就开工目标漂移是必然（P28）规格先行：改什么/不改什么/怎么验收
✗ 只压缩不落盘有损压缩 → 自信的错误（P39）结论先落盘，过程才允许压缩
✗ 把记忆当"垃圾桶"召回一堆过程，没有结论一条记忆 = 一个事实 + 来源 + 时间
✗ 只凭感觉判断"变好了"无法归因，无法证明first-pass 率 + 每通过任务花费（P49）

尾声 · 收束

三句话，带走整场课

01 大模型是一台只会预测下一个词的概率机器

它的强项（流畅、泛化）与弱点（幻觉、过期、失忆）来自同一件事——这不是 bug，是本性。对策只能工程化，不能许愿。

02 Harness 是把机器接进真实工程的那套马具

六大件（装配/工具/沙箱/记忆/验证/观测）没有一件让模型更聪明，都在补结构性漏洞。七顽疾 → 五零件，一张台账管完。

03 生产力 = 约束得多好 × 记得多牢

约束靠权限、验证、任务卡；记忆靠落盘、检索、版本化。这两件事都不在提示词里，在你的工程里。
